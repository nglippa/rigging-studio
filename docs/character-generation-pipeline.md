# Prompt-to-rig character pipeline

## Product entry and route behavior

`/` opens the full Rig Editor directly. It does not show a marketing, demo, or limited-access page. The editor top bar exposes **Create character**, which opens `/create-character`.

The workspace is a compact six-stage flow:

1. **Describe** — enter the natural-language brief and optional art controls.
2. **Generate** — review source art, run the structured suitability check, regenerate, or request a variant.
3. **Prepare** — review part boxes, labels, pivots, masks, semantic types, draw order, and explicit occlusion decisions.
4. **Rig** — review the generated hierarchy, drag joints, edit parents and transforms, inspect slots, and run a ±20° joint rotation check.
5. **Test** — run deterministic schema, pivot, equipment, occlusion, and major-joint smoke checks.
6. **Edit** — write a validated local handoff and open the generated character in the full Rig Editor.

Going backward preserves accepted work. The current `GeneratedCharacterProject` autosaves to local browser storage. **New** explicitly discards that character-project draft after confirmation.

## Prompt construction

`src/character-generation/prompt` owns the `MODULAR_2D_RIG_CHARACTER` preset. User prose remains primary. Structured controls are optional and are converted into provider-neutral guidance. The builder adds consistent instructions for one side-view character, a neutral pose, visible hands and feet, separable limbs and equipment, clean edges, simple or transparent background, and no perspective, motion blur, duplicate limbs, text, or scenery.

The internal generated prompt is hidden unless **Prompt debug** is enabled.

## Provider boundary

`CharacterPipelineProvider` is a capability-based interface for:

- image generation, regeneration, and variants;
- rig-suitability review;
- part segmentation;
- occlusion reconstruction;
- optional remote rig proposal;
- optional visual rig validation.

Every response has a strict TypeScript shape and Zod validation at the adapter boundary. `HttpCharacterPipelineProvider` sends `{ capability, body }` to a configured server endpoint. The browser never receives or stores a provider API secret. The server endpoint is responsible for authentication and translating a model-specific response into the project schemas.

Without `NEXT_PUBLIC_CHARACTER_PIPELINE_ENDPOINT`, the workspace uses `MockCharacterPipelineProvider`. This deterministic offline provider runs the complete controlled fantasy-knight scenario using the existing transparent part fixtures. It is a development path, not a claim that new artwork was generated by a live model.

Failures do not clear prior stage data. A failed generation preserves the brief; a failed segmentation preserves the source image; a failed reconstruction preserves the visible fragment; a failed rig proposal preserves accepted parts.

## Segmentation and transparent extraction

The initial taxonomy covers torso, head, bilateral upper arms/forearms/hands, thighs/lower legs/feet, plus hair, helmet, face, shoulders, cape, tail, main/off-hand equipment, accessories, and back equipment.

A proposed part contains confidence, source bounds, optional alpha mask, pivot hint, bone and slot suggestions, z-index, warnings, and provenance. Validation reports duplicate IDs, out-of-image crops, out-of-bounds pivots, and missing or duplicated recommended semantics.

The preparation overlay supports:

- accept/reject and rename;
- semantic reassignment;
- add, remove, merge-with-prior, and simple 50/50 split;
- numeric crop, pivot, draw-order, and bone changes;
- add-to-mask and remove/eraser brushes;
- mask reset.

`extractPartPixels` copies source RGBA pixels without resampling, multiplies rather than replaces source alpha, and can add transparent rotation padding. The browser path exports PNG data URLs. Pixel-art providers can preserve nearest-neighbor source assets; the processor itself does not interpolate pixels.

The mask tool is deliberately not a Photoshop replacement. It uses a circular brush over one per-part alpha mask; polygon tools, feathering, and content-aware edge refinement are future extensions.

## Occlusion repair

Likely hidden regions are flagged when provider warnings describe overlap, occlusion, or coverage beneath another part. Each flagged part requires a visible decision:

- keep the visible fragment;
- request a reconstruction;
- mark the fragment acceptable;
- regenerate the source.

A reconstruction is labeled, shown beside the original fragment, and remains unaccepted until the user explicitly chooses **Accept**. Rejection removes the proposed reconstructed image and keeps the original fragment. The mock adapter returns the clean fixture part so this behavior can be tested without a paid call.

Image-based hidden-area reconstruction is inherently uncertain. It can invent costume seams, anatomy, or lighting that was not observable in the source. The joint rotation check is therefore a diagnostic, not proof of correct unseen geometry.

## Automatic rig generation

The proposal builder preserves the existing `RigDefinition` schema:

- bones contain transforms only;
- standalone part images become `AttachmentDefinition`s;
- every attachment maps through a `SlotDefinition`;
- the initial `default` skin maps slot IDs to attachment IDs;
- equipment remains in stable slots rather than animation data.

The hierarchy is `root → pelvis → torso → head`, bilateral arm chains under the torso, and bilateral leg chains under the pelvis. Equipment reuses hand/head/torso attachment points in this first pass. Reparenting is guarded by a cycle check.

Pivots start from the provider hint, are clamped inside the proposed source crop, and are converted into attachment-local pixels. Confidence is retained per generated bone. This is geometry-based estimation; it does not claim anatomical inference from hidden pixels.

Draw order starts from provider z-index values with a deterministic semantic fallback. The Rig step exposes every slot z-index for correction. If torso armor was not segmented separately, the project reports that it is baked into the torso and cannot be swapped independently.

## Project format and portability

`GeneratedCharacterProject` version 1 stores:

- current stage, project identity, prompts, and provider metadata;
- source-image reference and suitability response;
- segmentation data and accepted masks;
- extracted part images and provenance;
- reconstruction reviews and acceptance state;
- generated rig and skins;
- warnings and user-correction log;
- creation and update timestamps.

JSON import/export is useful for inspection. ZIP export writes:

```text
manifest.json
source.png
parts/<part-id>.png
rig/rig.json
generation/metadata.json
```

The ZIP writer uses a deterministic uncompressed archive. Import supports these tool-created archives and rewrites packaged source/part images to in-memory data URLs, including rig attachment paths. Arbitrary compressed ZIPs are intentionally unsupported in this pass.

## Rig Editor handoff

**Open in Rig Editor** validates the generated rig through the normal `safeParseRigDefinition` path, serializes the existing editor draft format, stores a one-use handoff message, and navigates to `/`. The editor consumes the handoff, enables bones, resets the viewport, displays validation status, and retains the normal immutable history/runtime separation.

No manual JSON copying is required.

## First real provider test

1. Run `npm install` and `npm run dev` in the repository.
2. Open the printed local URL. `/` is the full editor.
3. Click **Create character**.
4. In `.env.local`, set `NEXT_PUBLIC_CHARACTER_PIPELINE_ENDPOINT` to a same-origin or CORS-enabled server proxy. Do not put a model secret in this variable or client code.
5. Make that proxy accept `{ capability, body }` for `generate`, `regenerate`, `variant`, `suitability`, `segment`, and `reconstruct`, returning the documented schemas.
6. Restart the local dev server and confirm the status bar names the configured provider.
7. Use the prefilled knight brief or enter a new one, then follow Describe → Generate → Prepare → Rig → Test.
8. Resolve every hidden-area warning, inspect the joint rotation check, and click **Open in Rig Editor**.
9. In the editor, verify bones and validation, enter Animate mode, and load/test a compatible animation.
10. Return to Create character and export the `.character.zip` archive before clearing the local draft.

## Known limitations

- The built-in provider is a deterministic fixture; novel generation requires a configured server adapter.
- The source flow is single-view only and cannot infer convincing front/back art.
- Segmentation correction has brush masks, numeric crops, and basic merge/split rather than advanced raster editing.
- Automatic pivots are bounding-box and provider-hint estimates, not pose-estimation guarantees.
- The joint check reports structural risks but does not perform computer-vision gap detection in the local adapter.
- Existing generic animations may require bone-name mapping or author adjustment when a provider emits a different taxonomy.
# Generation provenance and managed imports

Every source generation records `generationMode`, `novelArtwork`, `provider`, and `sourceArtifact`. Fixture generations are always `generationMode: "fixture"` and `novelArtwork: false`. Configured remote providers return `provider_generated`; externally generated assets enter as `imported_external` with `novelArtwork: true`.

`character_import_generation` does not create a parallel pipeline. The MCP server copies approved PNG/JPEG input into `.rigging-studio/generations/`, detects dimensions from the bytes, and updates the active project’s normal `sourceImage` and `generationHistory`. Suitability, segmentation, reconstruction, rig proposal, and smoke-test commands consume that same source representation.

Explicit activation precedence is: the most recent project create/open/import command, then same-project UI mutations, then cold-start draft restoration, then the initial empty workspace. Drafts use per-project keys plus a separate active-project pointer. A draft restore cannot replace an explicitly activated project.
